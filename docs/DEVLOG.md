### Расхождения ТЗ и статей (следуем самосогласованной физике)

1. **Знак J (Delloye et al. 2023, ур. 1).** В статье напечатано
   `H = −Σ J_ij σ_i σ_j = −I` и `J_ij = −Σ_m Re(t_im t_jm)`. Эти две записи несовместимы:
   из `I_m = |Σ_i t_mi σ_i|²` следует `I = Σ_ij σ_i σ_j Re Σ_m t_mi conj(t_mj)`, т.е.
   `J_ij = +Re Σ_m t_mi·conj(t_mj)` (как в ТЗ). Принимаем форму из ТЗ; обязательный тест
   «H через T == H через J» это проверяет.
2. **Overlap реплик.** Delloye определяет `q_αβ = 1 − |Σ_i (X_i^α − X_i^β)|/N` (в тексте
   формула, судя по всему, искажена при вёрстке) и строит распределение `P(|q|)`. Мы
   реализуем стандартный параметр Паризи `q = (1/N) Σ σ_i^α σ_i^β` и используем `|q|`,
   потому что H инвариантна к глобальному перевороту σ → −σ (интенсивность не меняется
   при умножении поля на −1). Как и в статье, q считается по «зоне интереса» — спинам,
   которые реально связаны с целевыми модами (см. этап 2).
3. **Batch-flip.** В эксперименте Delloye группа уменьшается от 12% пикселей до 1
   (последние ~600 итераций — по одному спину); в их численной модели переворачивают по
   одному спину, ~10N итераций до плато. Реализуем расписание «от initial_batch_fraction
   к 1 спину», доля — параметр процедуры.
4. **SPR / DPR / MPR (Zhao & Chi 2020).** SPR = GS, где Фурье-преобразование заменено
   Fresnel-преобразованием на расстояние z — ложится в общий интерфейс
   «пропагатор + целевая амплитуда → фазовая маска». DPR/MPR используют каскад из 2..n
   фазовых масок в разных плоскостях (в статье — для шифрования изображений); в нашей
   схеме один SLM, поэтому они оставлены как `TODO(later)`.

## Этап 1. Device Registry и Safety Validator

**Что сделано**
- `schemas/devices.py`: у `ParameterSpec` появился `default` (только для необязательных
  параметров); новый `RegistryDocument` (корень файла реестра: `name`,
  `simulation_only`, `notice`, `devices`); проверки уникальности id устройств, операций и
  параметров; методы `DeviceSpec.operation()` / `OperationSpec.parameter()`.
- `devices/yaml_registry.py` — `YamlDeviceRegistry`: читает YAML, валидирует Pydantic'ом и
  **при загрузке** проверяет, что каждый default сам проходит проверку своей спецификации.
- `devices/validator.py` — `SafetyValidator`: проверяет каждую команду
  (unknown_device / unknown_operation / unknown_parameter / missing_parameter / wrong_type /
  wrong_unit / out_of_range). Ничего не исправляет и не обрезает.
- `configs/devices/simulation.yaml` — вымышленные sim-устройства по ролям + виртуальное
  устройство `procedures` (calibrate_transmission_matrix, run_ising_optimization, focus).

**Ключевые решения и почему**
- **Строгие типы.** `bool` никогда не считается числом (в Python `True` — это `int`!),
  а `5.0` не принимается для `int`-параметра. LLM получит понятное сообщение и исправит.
- **NaN/inf отклоняются явно.** Сравнения с NaN всегда False, поэтому без отдельной
  проверки `nan` «прошёл» бы любой диапазон.
- **Единицы — точное совпадение**, без конвертации (мВт ≠ Вт): конвертация — место для
  ошибок, а LLM пусть пишет ровно то, что в реестре.
- **Defaults в реестре, а не в коде backend.** Это тоже «факты об устройстве», поэтому их
  источник — только реестр. Backend берёт defaults из реестра.
- **Параметры команд — только скаляры.** Целевые моды задаются как `n_targets` +
  `target_separation` (в макропикселях), а не списком — проще проверять диапазоны.
- **N ≤ 256** через `grid_side ≤ 16` (N = grid_side²) — тесты остаются быстрыми.
- **Генератор → среда** — явно помеченная гипотеза симуляции в описании устройства.

**Новые понятия**
- *Defense in depth* (эшелонированная защита): одна и та же проверка выполняется в
  нескольких местах (оркестратор перед `execute()` и сам hardware backend), чтобы ошибка
  в одном слое не пропустила опасную команду к устройству.

## Этап 2. Scientific Core: оптика, модели T, Изинг, метрики

**Что сделано** (`src/experimental_system/scientific_core/`)
- `geometry.py` — квадратные сетки SLM (N = side²) и камеры (M = side_cam²) в одной системе
  координат (единица — макропиксель SLM); детерминированный выбор целевых мод
  (`n_targets` + `separation`).
- `transmission.py` — модели T: **UTC** (i.i.d. circular Gaussian, дисперсия 1/N — толстый
  рассеиватель, all-to-all) и **тонкий рассеиватель** `T = g ⊙ w`,
  `w_mi = exp(−d_mi²/(2ℓ²))`, с нормировкой строк.
- `optics.py` — кодирование спинов фазой (+1→0, −1→π), `E_out = T·E_in` (одиночно и
  батчем), квантование фазы SLM, `CameraModel` (8 бит, насыщение 255, экспозиция и
  мощность масштабируют сигнал, read-шум + shot-подобный шум).
- `ising.py` — J через T, H оптически и через J, точный минимум перебором (N ≤ 20),
  относительный energy gap, намагниченность, overlap Паризи, зона интереса.
- `metrics.py` — построчная корреляция T (инвариантна к фазе строки), enhancement η,
  теория `π/4·(N−1)/N_f + 1`, детектор плато.

**Ключевые решения и почему**
- **Фиксированный беспорядок + огибающая.** В тонкой модели случайная часть `g` хранится
  отдельно, а напряжение генератора меняет только ℓ. Так «та же среда при другом
  напряжении» описывается согласованно, и сравнение двух напряжений в сценарии 3
  физически осмысленно (а не «две случайные среды»).
- **Нормировка «средняя интенсивность моды ≈ 1»** для случайного входа: тогда η = I_focus
  буквально, и масштаб камеры (gain·мощность·экспозиция) настраивается понятно.
- **Перебор основного состояния использует симметрию** H(σ) = H(−σ): фиксируем σ₀ = +1 и
  считаем 2^(N−1) конфигураций векторизованно кусками — N = 16 занимает миллисекунды.
- **Многофокусная теория.** Huang et al.: для N_f фокусов «добавить N_f в знаменатель» —
  трактуем как `π(N−1)/(4N_f) + 1` (знаменатель первого слагаемого). Для бинарной 0/π
  модуляции эта формула не используется (как требует ТЗ).

**Новые понятия**
- *UTC-модель*: каждый элемент T — независимая комплексная гауссова величина; свет из
  любого пикселя SLM попадает в любую моду камеры (полностью связанная система спинов).
- *Матрица Маттиса*: при одной целевой моде `J_ij = Re(t_i·conj(t_j))` имеет ранг ≤ 2, т.е.
  задача проще общего спинового стекла — поэтому одна мода даёт «ферромагнитное»
  основное состояние (с точностью до калибровочного узора фаз t_i).

## Этап 3. Phase retrieval: GGS и GS

**Что сделано** (`scientific_core/phase_retrieval.py`)
- `generalized_gs` — GGS 1 / GGS 2 / GGS 2-1 (Huang et al. 2021, ур. 3–4): псевдообратная
  `P⁺` считается один раз, остановка строки по корреляции `X_f` с `X_{f−2}` > 0.999999,
  сошедшиеся строки исключаются из итераций, максимум 1000 итераций на стадию.
- `focusing_phases` — фазовое сопряжение `φ_i = −Arg(x̂_mi)` (для двух фокусов — сумма строк).
- Общий интерфейс `Propagator` (forward/backward) и одна функция `gerchberg_saxton`:
  `FourierPropagator` — классический GS; `FresnelPropagator` — SPR (Zhao & Chi);
  `MatrixPropagator` — GS через известную T (целевая картина через рассеивающую среду).
- DPR/MPR — `TODO(later)` с описанием в docstring модуля (нужен каскад фазовых плоскостей).

**Проверка против статьи** (N = 64, γ = 4, без шума, seed фиксирован)

| Алгоритм | корреляция строк T | η / η_теор |
|---|---|---|
| GGS 1 | 0.73 | 0.65 |
| GGS 2 | 0.94 | 0.86 |
| GGS 2-1 | 1.00 | 0.98 |

Совпадает с Huang et al. (Fig. 2: GGS 2-1 ≈ 98%, GGS 2 ≈ 87%, GGS 1 застревает в
локальных оптимумах). Тест фиксирует порядок `GGS 2-1 > GGS 2 > GGS 1`.

**Ключевые решения**
- Корреляция для остановки берётся по модулю скалярного произведения — инвариантна к
  фазе строки (как и метрика качества T).
- В `MatrixPropagator` обратный шаг — псевдообратная `T⁺` (решение наименьших квадратов),
  а не `T†`: при M < N это точнее восстанавливает поле на SLM.

**Новые понятия**
- *Псевдообратная матрица (Мура–Пенроуза)* `P⁺`: «лучшее возможное обращение»
  неквадратной матрицы. Для переопределённой системы `P·x = e` (L > N уравнений) даёт
  решение наименьших квадратов: `x = P⁺·e`. Пример: `np.linalg.pinv(P) @ e`.
- *Phase retrieval*: камера измеряет `|E|²`, фаза теряется. GS-подобные алгоритмы
  чередуют два ограничения («амплитуда такая, как измерено» и «решение линейно / маска
  фазовая»), пока оценка не перестанет меняться.

## Этап 4. Optimization Engine: быстрый внутренний цикл

**Что сделано** (`optimization/inner.py`)
- Общий интерфейс `InnerOptimizer.run(objective, n_spins, n_iterations, rng)`;
  `objective` — *измерение* (счёт камеры в целевых модах), которое надо максимизировать.
  Оптимизатор никогда не видит T или J — как в реальной установке.
- `BatchFlipOptimizer` (Delloye): случайная группа спинов переворачивается, принимается,
  если интенсивность выросла; размер группы линейно падает от `initial_batch_fraction·N`
  до 1 за первые 70% итераций, остальные 30% — по одному спину.
- `SimulatedAnnealingOptimizer`: Метрополис по одному спину, геометрическое расписание
  температуры, температура *относительная* (умножается на стартовое значение objective).
- `make_optimizer(name, …)` — фабрика; имена совпадают с `choices` в реестре.
- Результат: лучшая конфигурация, траектория «лучшее на текущий момент», число измерений.

**Проверка** (N = 16, UTC, одна мода, 10 задач): 10 итераций → медианный gap ≈ 0.5;
100–200 итераций (~10N) → основное состояние в ~90–95% случаев. Согласуется с Delloye
(«~10N итераций достаточно для плато»). Это основа сценария 1: слабый план (мало итераций)
не проходит критерий, исправленный проходит.

**Ключевые решения**
- **Одна итерация = одно измерение** (SLM + кадр). Тогда `n_iterations` — это бюджет
  измерений, понятный и для симуляции, и для железа.
- **Относительная температура SA**: абсолютная шкала зависит от мощности лазера и
  экспозиции; относительная делает параметр переносимым между настройками.

**Новые понятия**
- *Protocol* (структурная типизация): класс подходит интерфейсу, если у него есть нужные
  методы/свойства — наследоваться не нужно. mypy проверяет это статически.
- *Метрополис*: худшее решение принимается с вероятностью `exp(Δ/T)`; при высокой T это
  помогает выбраться из локальных оптимумов, при T → 0 алгоритм становится жадным.

## Этап 5. Storage, Simulation backend, вычисление метрик

**Что сделано**
- `storage/run_store.py` — `RunStore`: `runs/<id>/state.json`, `iterations/iter_XX.json`,
  `arrays/*.npy` (возвращает `data_ref` вида `arrays/it01_0003_s1_tm_estimate.npy`),
  `llm_calls.jsonl`, `final_report.md`. Запись атомарная (tmp + rename), `load_array`
  отклоняет пути вне `arrays/` (защита от `../`).
- `backends/simulation.py`:
  - `SimulationWorld` — «скрытая истина» лаборатории (тип среды, seeds, шум, размер
    камеры). Задаётся сценарием/CLI, агентам недоступна.
  - `SimulationBackend` — состояние устройств (лазер, SLM, генератор, камера) +
    процедуры `calibrate_transmission_matrix`, `run_ising_optimization`, `focus` и
    `capture`. Внутренний цикл (тысячи масок и кадров) крутится здесь, наружу уходят
    только скаляры и `data_ref`.
  - **Повторная валидация каждой команды** внутри backend (defense in depth) — дёшево,
    поэтому делаем и в симуляции, не только в будущем hardware backend.
  - Ошибки процедур (нет сигнала, нет калибровки, устройство offline) → `ExecutionError`,
    выполнение пачки останавливается, статус PARTIAL/FAILED. Аналитик видит причину.
- `scientific_core/catalog.py` — **единственный список имён метрик** с описаниями
  (его получает Scientist в промпт).
- `scientific_core/evaluation.py` — `ExecutionResult → Metrics`: загружает массивы по
  `data_ref`, считает энергию/gap/overlap/η/корреляцию T функциями scientific_core и
  проверяет критерии успеха (`evaluate_criteria`).

**Ключевые решения и почему**
- **Фазовый bias из калиброванной T (отклонение от исходного плана, важно).** Первая
  версия сценария 3 без bias не показала эффекта Delloye (|q| не рос с ℓ). Причина: у
  Delloye «намагниченные» основные состояния получаются потому, что «spins and bias (from
  the TM [14]) are encoded by the SLM» (техника Jacucci et al. 2022). Без bias широкая
  среда — фрустрированное спиновое стекло. Добавлен параметр
  `run_ising_optimization.bias = none | calibrated_tm` (маска = фаза спина −Arg(Σ строк
  целевых мод калиброванной T)). Численная проверка (N = 36, 2 фокуса, sep = 3):
  ℓ ≈ 1 → |q| ≈ 0.5–0.6 (регионы независимы, «50%» у Delloye), ℓ = 3 → |q| ≈ 0.9
  (регионы связаны). Сценарий 3 теперь честно требует калибровки при каждом напряжении.
- **`Measurement.command_index`** (расширение схемы). Несколько команд могут иметь один
  `step_id`; без индекса evaluation склеивал измерения калибровки и оптимизации
  (найдено на пробном прогоне: `tm_correlation` 0.2 вместо 0.98).
- **Автоэкспозиция в процедурах** (детерминированный HDR): предварительный скан
  подбирает экспозицию так, чтобы пик был на 60–90% шкалы; в оптимизации экспозиция
  делится пополам при насыщении целевой моды; значения нормируются на мс. Иначе фокус
  (в ~50 раз ярче спекла) всегда упирался бы в 255.
- **Проверка «есть ли сигнал»** — по кадрам, а не по внутреннему флагу лазера: так же
  будет работать и на железе.
- **Энергия считается по «эталонной» T**: в симуляции — истинная T (с учётом bias), на
  железе будет калиброванная. `tm_correlation` помечена как simulation-only.
- **Метрики при нескольких запусках оптимизации**: основные — по последнему запуску,
  `replica_overlap_change` = последний − первый (для сравнения двух напряжений).

**Новые понятия**
- *data_ref*: вместо массива в контракте лежит ссылка на файл. LLM видит «tm_estimate:
  1024 элемента, arrays/…npy», но никогда не видит сами числа.
- *Атомарная запись*: пишем во временный файл и переименовываем; при сбое не останется
  наполовину записанного `state.json`.

## Этап 6. LLM-слой

**Что сделано** (`llm/`)
- `config.py`: модели по агентам (`SCIENTIST_MODEL`, `EXPERIMENT_MODEL`, `RUNNER_MODEL`,
  `ANALYST_MODEL`) с общим `DEFAULT_MODEL`; в коде **нет ни одного имени модели** —
  `Settings.model_for()` бросает понятную ошибку, если ничего не задано. Плюс OpenRouter,
  Pinecone, лимиты (`EXPSYS_MAX_LLM_CALLS`, `EXPSYS_MAX_ITERATIONS`), `EXPSYS_RUN_LIVE`.
- `openrouter.py` — `OpenRouterClient` (через пакет `openai`, `base_url` OpenRouter):
  `json_schema` → при HTTP 400 автоматически переключается на «JSON в тексте» и
  запоминает это до конца прогона → Pydantic-валидация → повтор с текстом ошибки
  (до 3 попыток) → `StructuredOutputError`. Сетевой вызов спрятан за `ChatTransport`,
  поэтому вся логика fallback/retry тестируется без сети.
- `structured.py` — инструкция со схемой, извлечение JSON из ответа (markdown-блоки,
  текст вокруг), понятные LLM сообщения об ошибках валидации.
- `fake.py` — `FakeLLM`: очередь заготовленных ответов на агента; ответы проходят ту же
  Pydantic-валидацию, что и настоящие.
- `tracking.py` — `LoggedLLM` (одна строка JSONL на вызов: агент, модель, время,
  попытки, режим, токены, ошибка) и `CallBudget` (лимит вызовов на прогон →
  `LLMBudgetExceededError` → FAILED с понятным сообщением).
- `factory.py` — `build_clients("fake" | "openrouter", …)` → по клиенту на агента.

**Ключевые решения**
- **Инструкция со схемой добавляется всегда**, даже в режиме `json_schema`: через
  OpenRouter часть провайдеров молча игнорирует `response_format`; лишние токены
  дешевле лишней попытки.
- **`strict: false`** в json_schema: strict-режим OpenAI требует, чтобы все поля были
  обязательными, а наши схемы имеют defaults. Валидацию всё равно делает Pydantic.
- **Лимит считает вызовы агентов** (`generate`), каждый ≤ `EXPSYS_LLM_MAX_ATTEMPTS`
  HTTP-запросов → стоимость прогона ограничена сверху `max_llm_calls × max_attempts`.
- Tool calling — `TODO(later)` (json_schema + текстовый fallback покрывают все модели).
- Модуль назван `tracking.py`, а не `logging.py`, чтобы не путать со стандартным `logging`.

**Новые понятия**
- *Structured output*: просим модель вернуть JSON по схеме и сразу валидируем его в
  Pydantic-объект. Если модель ошиблась, отправляем ей текст ошибки и просим исправить —
  это обычно работает со второй попытки.
- *Generic-метод* `def generate[T: BaseModel](…, response_model: type[T]) -> T`
  (синтаксис Python 3.12): тип результата выводится из переданного класса, mypy знает,
  что `generate(msgs, AnalysisReport)` возвращает `AnalysisReport`.

## Этап 7. Knowledge Base

**Что сделано** (`knowledge/`, `data/knowledge/cards/`)
- `ingest.py`: PDF → текст страниц (pymupdf) → разделы (эвристика заголовков: нумерованные
  «2.1. …», «II. …» и стандартные имена разделов) → чанки ~650 токенов с перекрытием ~100
  → `KnowledgeFragment` с метаданными `paper`, `section`, `page`, `file`. Список
  литературы, благодарности и funding пропускаются (шум для поиска). Короткие разделы
  склеиваются со следующими.
- 8 карточек знаний (`data/knowledge/cards/*.md`, YAML front matter: id, title, source,
  tags): энергия через интенсивность, J через T, поиск основного состояния, overlap
  реплик, GGS, enhancement, метрики качества T, GS/SPR/DPR/MPR. У каждой — ссылка на
  статью (и на уравнение/раздел).
- `memory.py` — `InMemoryKnowledgeBase`: BM25 (без внешних зависимостей), фильтры по
  метаданным, сохранение/загрузка локального индекса в JSONL
  (`data/knowledge/index/fragments.jsonl`, в `.gitignore`).
- `pinecone_kb.py` — `PineconeKnowledgeBase`: integrated embedding (Pinecone сам
  считает эмбеддинги), `field_map={"text": "chunk_text"}`, namespace `papers`, upsert
  пачками по 96, фильтры `{"k": {"$eq": v}}`. Имя индекса, модель эмбеддингов, облако и
  регион — только из настроек. Индекс создаётся лишь явной командой `expsys ingest`.

**Ключевые решения**
- **Детерминированные fragment_id** (`<slug файла>:p<страница>:c<номер>`, `card:<id>`):
  повторный ingest обновляет те же записи, а цитаты Scientist'а остаются валидными.
- **Карточки на английском**: статьи на английском, лексический поиск по одному языку
  работает лучше; агенты тоже получают промпты на английском.
- **Мусорные заголовки PDF** («Article», «untitled») заменяются именем файла.
- Pinecone-код тестируется через фейковый индекс с тем же интерфейсом (`upsert_records`,
  `search`); реальный вызов — только в `@pytest.mark.live`.

**Новые понятия**
- *BM25*: классическая формула лексического ранжирования: слово весит больше, если оно
  редкое в коллекции (IDF) и частое в документе, с насыщением по частоте и поправкой на
  длину документа.
- *Integrated embedding*: векторная БД сама превращает текст в вектор моделью, указанной
  при создании индекса; мы отправляем и ищем просто текст.
- *Chunking с перекрытием*: соседние куски делят ~100 токенов, чтобы мысль на границе не
  потерялась.

## Этап 8. Агенты

**Что сделано** (`agents/`, `prompts/*.md`)
- `common.ask_checked` — общий цикл каждого агента: «контекст (JSON) →
  `llm.generate(ResponseModel)` → детерминированные проверки → если есть замечания,
  вернуть их модели и повторить (≤ 3 раз) → `AgentError`». Вывод, не прошедший проверки,
  никогда не возвращается.
- `scientist.py` — ищет в KB по задаче (+ обоснованию Analyst при REMODEL), отдаёт
  фрагменты и **список метрик из каталога**. Проверки: каждая цитата — из выдачи поиска;
  хотя бы одна цитата; критерии только по метрикам каталога; при REMODEL спецификация
  должна измениться. Устройств не видит вообще.
- `experiment.py` — получает спецификацию и обзор устройств/процедур **без диапазонов**.
  Проверки: устройства существуют; при REPLAN план не совпадает с прошлым.
- `runner.py` — получает план, **полный** реестр (типы, единицы, диапазоны, defaults) и
  статусы; при повторе — нарушения от Safety Validator. Проверки: `step_id` из плана,
  устройство не offline. Цикл «валидатор отклонил → Runner исправляет» (≤ 2 раз)
  реализован в оркестраторе (этап 9).
- `analyst.py` — получает спецификацию, план, сводку исполнения (скаляры, без массивов) и
  Metrics. Проверка: `referenced_metrics` ⊆ вычисленных метрик.
  **Правило в коде: DONE принимается только при `all_criteria_met`; иначе решение
  переводится в REPLAN**, а в рекомендации добавляется код-генерированный список
  невыполненных критериев (с наблюдаемыми значениями из Metrics).
- `context.py` — **память между итерациями**: компактные сводки каждого прошлого круга
  (план, статус исполнения, метрики, критерии, решение, рекомендации). При REPLAN
  Experiment получает прошлый план + историю + рекомендации; при REMODEL Scientist —
  прошлую спецификацию + обоснование Analyst. Промпты и проверки в коде запрещают
  повторять неудачный план/спецификацию без изменений.

**Ключевые решения**
- **Промпты на английском** (их читает LLM; англоязычные модели и статьи), отдельными
  файлами в пакете (`importlib.resources`).
- **Контекст — один JSON-документ** в user-сообщении: агент видит ровно то, что ему
  положено (разделение информации проверяется тестами: в контексте Scientist нет слова
  «device»).
- Повторы по замечаниям тратят бюджет LLM-вызовов (каждый `generate` считается).

**Новые понятия**
- *Post-validation*: LLM — генератор гипотез, код — судья. Любое правило, которое можно
  проверить кодом (существование устройства, цитаты, имена метрик, DONE vs критерии),
  проверяется кодом, а не «просьбой в промпте».

## Этап 9. Оркестратор (LangGraph), persistence, отчёт, сценарии

**Что сделано**
- `orchestrator/graph.py` — граф LangGraph: `scientist → experiment → runner → validate →
  execute → metrics → analyst → route → (scientist | experiment | finalize)`;
  `validate → runner` при отказе (≤ 2 исправлений, затем FAILED); любое исключение в
  узле → FAILED с текстом ошибки, частичная итерация сохраняется в history.
- **Лимиты**: `max_iterations` → ITERATION_LIMIT; бюджет LLM-вызовов
  (`EXPSYS_MAX_LLM_CALLS`, по умолчанию 40) → FAILED «LLM call budget exhausted …».
- `require_approval`: перед `execute()` вызывается `approver(commands)`; отказ → ABORTED.
- Перед `execute()` оркестратор ещё раз прогоняет валидатор (и backend — сам), т.е.
  непроверенная команда физически не может дойти до устройства.
- Persistence: `state.json` после **каждого** узла, `iterations/iter_XX.json` в конце
  каждого круга, `arrays/itXX_*.npy`, `llm_calls.jsonl`, `final_report.md`.
- `orchestrator/report.py` — детерминированный отчёт на русском: задача, постановка,
  план/команды/исполнение/метрики/критерии/решение по каждой итерации, сводная таблица
  метрик по итерациям, итог, источники (цитаты → статья, раздел, страница).
- `scenarios.py` + `configs/scenarios/*.yaml`: задача + мир симуляции + ответы FakeLLM.
- `app.py` — единая сборка компонентов для CLI и e2e-тестов.

**Ключевые решения и почему**
- **Один канал состояния.** LangGraph хранит только `{"exp": ExperimentState}`, узлы —
  чистые функции `state → state` над неизменяемой Pydantic-моделью. Так не нужно
  разбираться с reducer'ами каналов LangGraph, а узлы легко тестировать.
- **`recursion_limit` вычисляется** из `max_iterations` (`(8 + 2·2)·N + 10`): дефолт
  LangGraph (25 шагов) закончился бы уже на второй итерации.
- **Approval — синхронный callback**, без checkpointer/interrupt: для CLI этого
  достаточно; для API позже можно заменить на `interrupt()` LangGraph.
- **Поиск Scientist'а: сначала карточки (top 4), затем вся база (top 6).** Курируемые
  формулы всегда в контексте, и сценарии FakeLLM не зависят от того, проиндексированы
  ли PDF локально.
- **Сценарий 3 и разброс реализаций среды.** Рост |q| от слабой к сильной связи
  положителен для всех 6 проверенных реализаций тонкой среды, но величина колеблется от
  +0.13 до +0.50 (10 реплик — мало статистики). Для демо закреплён `medium_seed: 3`
  (+0.39). Это честная особенность малого N, а не подгонка физики.
- **enhancement_ratio может быть чуть > 1** (в сценарии 2 ≈ 1.04): опорная интенсивность
  ⟨I⟩ оценивается по 200 случайным маскам (~7% статистической погрешности), а теория —
  среднее по ансамблю.

**Сценарии и их результат (FakeLLM)**

| Сценарий | Итог | Ключевые метрики |
|---|---|---|
| `ising_ground_state` | REPLAN → DONE | energy_gap 0.279 → 0.0 |
| `tm_calibration_focusing` | DONE | tm_correlation 0.98, enhancement_ratio ≈ 1.0 |
| `two_foci_coupling` | DONE | replica_overlap_change ≈ +0.39 |
| `runner_out_of_range` | 1 отказ валидатора → DONE | 500 мВт отклонено, принято 50 мВт |

**Новые понятия**
- *State machine*: система всегда находится в одном явном состоянии (узел графа), а
  переходы описаны условиями. Нельзя «случайно» выполнить команду, минуя `validate`:
  такого ребра в графе просто нет.
- *recursion_limit*: защита LangGraph от бесконечных циклов — максимальное число шагов
  графа за один `invoke`.
