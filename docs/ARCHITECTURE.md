# Архитектура Agentic Experimental System

Документ описывает, как устроена система, из каких компонентов она состоит и почему
сделано именно так. Обновляется на каждом этапе (история решений — в `DEVLOG.md`).

## 1. Идея в одном абзаце

Система получает научную задачу (`TaskRequest`) и сама проводит эксперимент: LLM-агенты
решают *что* делать (формулировка, план, команды устройствам, интерпретация), а
детерминированный Python-код делает всё, где важны числа и безопасность (физика, метрики,
оптимизация, проверка команд). Сейчас эксперимент выполняется в симуляции; железо будет
подключено позже через тот же интерфейс backend.

## 2. Цикл эксперимента

```
TaskRequest
   │
   ▼
┌───────────┐ системный промпт ┌────────────────┐
│ Scientist │◄─────────────────│ Knowledge pack │   (все карточки целиком, без поиска)
└─────┬─────┘                  └────────────────┘
      │ ScientificSpecification (критерии успеха = метрики scientific_core)
      ▼
┌────────────┐   список устройств/процедур (без диапазонов)
│ Experiment │◄────────────── Device Registry
└─────┬──────┘
      │ ExperimentPlan (шаги)
      ▼
┌────────┐   полные описания устройств + статусы
│ Runner │◄────────────── Device Registry / Backend
└───┬────┘
    │ CommandBatch                         ┌──── нарушения (≤ 2 исправления) ───┐
    ▼                                      │                                    │
┌──────────────────┐  отклонено ───────────┘                                    │
│ Safety Validator │───────────────────────────────────────────────────────────►Runner
└───┬──────────────┘
    │ принято (+ опционально подтверждение человека)
    ▼
┌────────────────────┐  быстрый внутренний цикл (тысячи измерений, без LLM)
│ Execution Backend  │  Simulation сейчас / Hardware позже
└───┬────────────────┘
    │ ExecutionResult (скаляры + data_ref на массивы .npy)
    ▼
┌─────────────────┐
│ Scientific Core │  Metrics + проверка критериев (детерминированно)
└───┬─────────────┘
    ▼
┌─────────┐
│ Analyst │──► DONE (только если все критерии выполнены)
└─────────┘──► REPLAN  → Experiment (с прошлым планом, историей метрик, рекомендациями)
           ──► REMODEL → Scientist  (с прошлой спецификацией и обоснованием)
           ──► ABORT
Ограничители: max_iterations → ITERATION_LIMIT; лимит LLM-вызовов / ошибки → FAILED.
```

## 3. Два цикла оптимизации

- **Быстрый внутренний** — внутри backend/Optimization Engine: перевернуть группу спинов,
  измерить интенсивность, принять/отклонить; тысячи итераций, чистый Python, **никогда не
  вызывает LLM**.
- **Медленный внешний** — агенты между запусками выбирают стратегию и параметры
  (алгоритм, число итераций, γ калибровки, напряжение генератора…).

## 4. Компоненты

### 4.1 Контракты (`schemas/`)
Все компоненты обмениваются Pydantic-моделями (`Contract`: `extra="forbid"`, frozen).
Лишнее поле от LLM — ошибка валидации, а не тихо проигнорированный мусор. Большие массивы
никогда не попадают в контракты: только `data_ref` (путь к `.npy`) и скаляры.

### 4.2 Device Registry (`devices/yaml_registry.py`, `configs/devices/*.yaml`)
Единственный источник фактов об устройствах: операции, параметры, типы, диапазоны,
единицы, defaults. Файл пишет и проверяет человек. `simulation.yaml` содержит вымышленные
устройства `sim_laser`, `sim_slm`, `sim_generator`, `sim_camera` (помечены «simulation only»)
и **виртуальное устройство `procedures`** — высокоуровневые детерминированные процедуры
(калибровка T, Изинг-оптимизация, фокусировка). Благодаря этому параметры процедур
(γ, число итераций, алгоритм…) проверяются тем же валидатором, что и напряжение.

### 4.3 Safety Validator (`devices/validator.py`)
Чистая функция «команда + реестр → список нарушений». Проверяет устройство, операцию,
имена параметров, обязательность, тип (строго: bool ≠ число, 5.0 ≠ int), единицу (точное
совпадение) и диапазон (включительно, NaN/inf отклоняются). Никогда не исправляет
значение: «вне диапазона» = отказ + сообщение Runner'у. Вызывается оркестратором перед
`execute()`; hardware backend в будущем обязан вызывать его повторно сам.

### 4.4 Scientific Core (`scientific_core/`)
Вся математика — чистый numpy, детерминированный при заданном seed.

| Модуль | Что внутри |
|---|---|
| `geometry.py` | сетки SLM/камеры в общих координатах, выбор целевых мод |
| `transmission.py` | модели T: UTC (толстый рассеиватель) и тонкий рассеиватель с длиной ℓ |
| `optics.py` | фазовое кодирование спинов, `E_out = T·E_in`, 8-битная камера с шумом и насыщением |
| `ising.py` | `J_ij = Re Σ_{m∈S} t_mi·conj(t_mj)`, `H = −Σ_{m∈S} I_m = −σᵀJσ`, перебор N ≤ 20, overlap |
| `metrics.py` | корреляция строк T, enhancement и его теория, плато |
| `phase_retrieval.py` | GGS 1/2/2-1 (калибровка T по интенсивностям), GS/SPR/GS-через-T за общим `Propagator` |

Ключевая модель: `E_in,i = exp(iφ_i)`, `E_out = T·E_in`, `I_m = |E_out,m|²`. Камера видит
только интенсивность (8 бит), поэтому T приходится восстанавливать алгоритмом (этап 3).

### 4.5 Optimization Engine (`optimization/`)
Быстрый внутренний цикл: оптимизатор получает функцию-измерение «спины → интенсивность в
целевых модах» и максимизирует её (batch-flip по Delloye или simulated annealing). Он не
знает ни T, ни J, ни того, симуляция это или железо — поэтому тот же код пойдёт на
реальную установку. LLM здесь никогда не вызывается; агенты выбирают алгоритм и бюджет
итераций *между* запусками.

### 4.6 Execution backends (`backends/`)
Общий интерфейс `ExecutionBackend`: `name`, `device_status()`, `execute(commands)`.
Агенты и оркестратор зависят только от него.

**SimulationBackend** = «мир» + устройства + процедуры:
- `SimulationWorld` — скрытая истина (UTC или тонкая среда, seeds, шум, размер камеры).
  Выбирается сценарием, как физический рассеиватель в лаборатории.
- Устройства хранят состояние (лазер вкл/мощность, сетка SLM, генератор, экспозиция).
- Процедуры (виртуальное устройство `procedures`) крутят быстрый цикл:
  - `calibrate_transmission_matrix`: L = γN случайных масок → кадры → `|E| = √(counts/ms)`
    → GGS → `T̂` (в `arrays/`);
  - `run_ising_optimization`: оптимизатор из `optimization/` с objective = «счёт камеры в
    целевых модах»; реплики, траектории, опционально фазовый bias из `T̂`;
  - `focus`: маска фазового сопряжения (или GS через `T̂`), измерение фокуса и опорного
    спекла (HDR-экспозиция);
  - `capture`: один кадр.
- Каждая команда **повторно проверяется Safety Validator'ом** внутри backend.
- Гипотеза симуляции (явно помечена): напряжение генератора → длина взаимодействия ℓ
  тонкой среды.

### 4.7 Вычисление метрик (`scientific_core/evaluation.py`, `catalog.py`)
`ExecutionResult` (скаляры + `data_ref`) → `Metrics`: числа считаются только здесь
(энергия, gap к точному минимуму, overlap реплик, η и η/η_теор, корреляция T, плато,
число кадров, насыщение). Затем `evaluate_criteria` детерминированно проверяет критерии
`metric op target`. `catalog.METRICS` — единый список имён: Scientist может ставить
критерии только по ним.

### 4.8 Storage (`storage/run_store.py`)
```
runs/<experiment_id>/
  state.json            # ExperimentState после каждого узла графа
  iterations/iter_XX.json
  arrays/*.npy          # маски, кадры, T — только по data_ref
  llm_calls.jsonl       # каждый вызов LLM: агент, модель, время, токены
  knowledge_pack.md     # точный текст knowledge pack, который видел Scientist
  final_report.md       # отчёт на русском
```

### 4.9 LLM-слой (`llm/`)
Агенты знают только `LLMClient.generate(messages, ResponseModel) -> ResponseModel`.

```
Agent ──► LoggedLLM (бюджет вызовов + llm_calls.jsonl)
             └──► OpenRouterClient (одна модель)     или   FakeLLM (сценарий)
                     ├─ json_schema (response_format)
                     ├─ HTTP 400 → JSON-в-тексте (запоминается)
                     └─ Pydantic-валидация → повтор с ошибкой (≤ 3) → StructuredOutputError
```
Модель задаётся для каждого агента отдельно (`SCIENTIST_MODEL`, …) с общим
`DEFAULT_MODEL`; имён моделей в коде нет. `FakeLLM` проигрывает ответы из сценария и
валидирует их так же строго, поэтому весь цикл работает офлайн и детерминированно.

### 4.10 Научные знания: knowledge pack (`knowledge/cards.py`, `data/knowledge/cards/`)
Только научные знания и только для Scientist (никогда не источник фактов об устройствах).
**Поиска нет**: все карточки целиком входят в системный промпт Scientist.
```
data/knowledge/cards/*.md  (YAML front matter: id, title, source, tags + markdown)
        │  CardDirectorySource.cards()   — парсинг и проверка каждой карточки
        ▼
list[KnowledgeCard]
        │  build_knowledge_pack(max_chars) — уникальность id, сортировка по id, лимит размера
        ▼
KnowledgePack(text, cards, sha256) ──► prompts/scientist.md + "\n\n" + pack.text
```
- Проверки при загрузке (ошибка = `KnowledgePackError` с именем файла): front matter
  есть и валиден, поля `id`/`title`/`source` заполнены, лишних ключей нет, `id` в
  snake_case и уникален, тело не пустое, итоговый текст ≤
  `EXPSYS_KNOWLEDGE_PACK_MAX_CHARS` (по умолчанию 60 000 символов ≈ 15k токенов).
- Текст пакета детерминирован (карточки по алфавиту id): одинаковые карточки → один и
  тот же промпт и sha256. Точный текст сохраняется в `runs/<id>/knowledge_pack.md`, хэш —
  в `state.json`.
- Scientist цитирует `card_id`; код проверяет, что каждая цитата — существующая карточка
  пакета, и что есть хотя бы одна цитата.
- Интерфейс источника — `KnowledgeSource.cards() -> list[KnowledgeCard]` (сейчас каталог;
  при росте объёма можно вернуть поиск, см. DEVLOG).

**Почему без RAG.** Статей три, карточек меньше десяти — весь объём помещается в промпт. Поиск
только добавлял риск, что нужная формула не попадёт в выдачу, и делал поведение
Scientist'а зависимым от индекса.

### 4.11 Агенты (`agents/`, `prompts/`)
Каждый агент = системный промпт (`prompts/<agent>.md`) + функция «контекст →
`llm.generate(ResponseModel)` → проверки в коде → повтор с замечаниями».

| Агент | Видит | Выдаёт | Проверки в коде |
|---|---|---|---|
| Scientist | задача, knowledge pack (в системном промпте), каталог метрик, (REMODEL: прошлая спецификация, обоснование, история) | `ScientificSpecification` | цитаты ⊆ id карточек пакета; метрики ∈ каталог; спецификация изменилась |
| Experiment | спецификация, устройства/процедуры **без диапазонов**, (REPLAN: прошлый план, рекомендации, история) | `ExperimentPlan` | устройства существуют; план изменился |
| Runner | план, **полный** реестр, статусы, нарушения валидатора | `CommandBatch` | step_id из плана; устройство доступно; + Safety Validator |
| Analyst | спецификация, план, сводка исполнения, Metrics, история | `AnalysisReport` | referenced_metrics ⊆ Metrics; **DONE → REPLAN, если критерии не выполнены** |

Разделение информации — намеренное: Scientist не может «подогнать» физику под
устройства, Experiment не тратит внимание на диапазоны, а единственный, кто видит
диапазоны, — Runner, и его всё равно проверяет код.

### 4.12 Оркестратор (`orchestrator/`)
```
START → scientist → experiment → runner → validate ─┬─(отклонено, ≤2)→ runner
                                                    └─(принято)→ execute → metrics → analyst → route
route: DONE → finalize        REPLAN  → experiment (iteration+1)
       ABORT → finalize       REMODEL → scientist  (iteration+1)
       лимит итераций → ITERATION_LIMIT → finalize
любая ошибка узла (LLM, агент, backend, бюджет) → FAILED → finalize → END
```
- Состояние — один неизменяемый `ExperimentState` в канале LangGraph; узлы — чистые
  функции; после каждого узла `state.json` сохраняется на диск.
- На каждом круге в `history` добавляется `IterationRecord` (спецификация, план,
  валидации, число исправлений Runner'а, исполнение, метрики, анализ).
- `require_approval` — пауза перед `execute()` с подтверждением в CLI.
- `finalize` пишет `final_report.md` (на русском) детерминированно из состояния.

### 4.13 Сценарии и сборка (`scenarios.py`, `app.py`, `configs/scenarios/`)
Сценарий = задача + `SimulationWorld` + (для FakeLLM) ответы агентов. `app.run_task`
собирает knowledge pack → registry → backend → LLM-клиенты (с логированием и бюджетом) → оркестратор;
CLI и e2e-тесты используют одну и ту же сборку.

### 4.14 CLI (`cli.py`)
- `expsys run "<задача>" --llm fake|openrouter [--max-iterations N] [--scenario <name>]
  [--approve]`;
- `expsys knowledge [--full]` — печатает knowledge pack (или весь системный промпт
  Scientist) теми же функциями, что строят промпт, т.е. байт в байт;
- `expsys show <experiment_id>`, `expsys scenarios`.
Ошибки конфигурации (нет ключа, нет модели, неизвестный сценарий) выдаются одной
строкой и проверяются **до** создания каталога прогона.

## 5. Конфигурация

Все настройки — `config.Settings` (pydantic-settings): переменные окружения и `.env`
(документированы в `.env.example`). Модели LLM — только в настройках (`DEFAULT_MODEL` +
`SCIENTIST_MODEL` / `EXPERIMENT_MODEL` / `RUNNER_MODEL` / `ANALYST_MODEL`). Пустая строка
(`KEY=`) означает «не задано».

## 6. Где проходят жёсткие правила

| Правило | Где обеспечено |
|---|---|
| LLM не считает | все числа: `scientific_core/*`, `evaluation.py`; Analyst получает готовые Metrics |
| Параметры устройств только из реестра | `configs/devices/*.yaml` → `YamlDeviceRegistry`; Runner видит только его |
| Каждая команда проверяется | `SafetyValidator` в узле `validate`, повторно перед `execute`, и внутри backend |
| Вне диапазона = отказ, не clamp | `check_value` только сообщает; тест проверяет, что значение не изменено |
| Лимит итераций и вызовов LLM | `route` → ITERATION_LIMIT; `CallBudget` → FAILED |
| Большие массивы не идут в LLM | backend → `.npy` + `data_ref`; сводки для агентов содержат только скаляры |
| `extra="forbid"` | базовый `Contract` всех схем |
| Цитаты Scientist реальны | проверка в `run_scientist`: каждый `card_id` есть в knowledge pack |
| DONE только при выполненных критериях | `run_analyst` переводит DONE → REPLAN |

## 7. Известные ограничения (MVP)

- Мир симуляции идеализирован: SLM без LUT-нелинейности и cross-talk, нет дрейфа среды
  во времени, шум камеры — простая гауссова модель, генератор → ℓ — гипотеза.
- `tm_correlation` доступна только в симуляции (нужна истинная T); на железе качество T —
  только через `enhancement_ratio`.
- Энергии Изинга в метриках считаются по «эталонной» T (в симуляции — истинной); на
  железе ими станет калиброванная T.
- Точный основной уровень — только для N ≤ 20; для больших N используются
  `plateau_fraction`, `replica_overlap`, `target_signal`.
- Tool-calling режим LLM, DPR/MPR — `TODO(later)`.
- Knowledge pack ограничен размером промпта; при росте базы знаний понадобится вернуть
  поиск (см. DEVLOG, «Как вернуть RAG»).
- Оркестратор синхронный; approval — callback в CLI (для API понадобится `interrupt`).

## 8. Что дальше

1. **Digital twin**: `SimulationWorld` → параметры, откалиброванные по реальной установке
   (LUT SLM, шум и битность камеры, дрейф T, задержки триггера), тот же интерфейс backend.
2. **Hardware backend** (MCP): реальный реестр `configs/devices/lab.yaml` после проверки
   человеком; backend **обязан** повторно валидировать каждую команду (уже так сделано в
   симуляции); обязательный `require_approval`; драйверы SLM (Blink SDK), камеры
   (`alkusb3`, внешний триггер), генератора, лазера (COM-порт).
3. Процедуры `procedures` переиспользуются как есть: они общаются с устройствами только
   через «показать маску / снять кадр».
